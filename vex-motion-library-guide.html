Introduction & Vision

What this document is and what you're building.

This guide is a reference for designing a VEX V5 motion library that combines the strengths of the two most popular community templates:

  • LemLib's pose-aware motions (moveToPoint, moveToPose boomerang, turnToPoint, pure pursuit), all driven by continuous odometry.
  • EZ-Template's ergonomic relative motions: "drive 24 inches straight," swing turns, robust PID exit conditions, and a dead-simple tuning workflow.

The key design insight that makes the hybrid work: every motion, relative or absolute, should update and consume the same global pose estimate. In EZ-Template, a "drive 24 inches" move is tracked only by encoder ticks relative to the start of that motion, so the robot doesn't know where it is on the field afterward. In your library, that same relative motion runs on top of the odometry task, so after driving 24 inches you can immediately call moveToPoint(72, 24) and it just works. Relative motions become conveniences that compute an absolute target from the current pose, not a separate tracking regime.

You're building two implementations of one design:

  • C++ on PROS 4 (FreeRTOS tasks, mature ecosystem).
  • Rust on vexide (async/await, no_std, memory safety).
How to read this guide Each algorithm section covers: what it is, what it's used for, pros/cons, and implementation considerations. The later sections cover library architecture (the part most templates get wrong) and the Rust-vs-C++ tradeoff. If you're new to this space, read Foundations → Odometry → PID → Move to Point first; everything else builds on those four.

Foundations: Pose & Coordinates

Get these conventions right on day one; they touch every line of math you'll write.

Pose

A pose is the robot's full planar state: position plus heading, written (x, y, θ). Every algorithm in this guide either estimates a pose (localization) or consumes one (motion control). Your library should have exactly one Pose type, used everywhere.

Pick a coordinate convention and never break it

The two common conventions in VEX:

Math-standard (WPILib-like)Compass-style (LemLib)
+x"East" / rightRight
+y"North" / upForward / up
θ = 0Along +xAlong +y (robot facing "north")
Positive rotationCounterclockwise (radians)Clockwise (degrees)
ProsMatches every math identity (atan2, rotation matrices) with no sign fudging; matches WPILib docs and papersMatches how drivers think ("heading 90 = facing right"); matches LemLib docs

Recommendation: use math-standard radians internally (all algorithm code), and expose compass-degrees at the API surface if you want LemLib-style ergonomics. Convert exactly once at the boundary. Mixed conventions inside algorithm code are the single most common source of "robot spins the wrong way" bugs.

Angle wrapping

Heading errors must be wrapped to (-180°, 180°] (or (-π, π]) before feeding a controller, or the robot will take the long way around. Write one well-tested helper and use it everywhere:

// wraps any angle to (-π, π]
fn wrap(angle) {
    return atan2(sin(angle), cos(angle))   // slow but bulletproof
    // or: remainder(angle, 2π)             // fast, uses IEEE remainder
}

Units

Decide units globally: inches vs meters, degrees vs radians, and stick to them internally. Both languages let you enforce this with types (see API Design). VEX-specific constants you'll need everywhere:

  • Field: 12 ft × 12 ft (144 in × 144 in); tiles are 24 in (technically ~23.8 in of usable foam each, but 24 in spacing).
  • Common wheel diameters: 2.75", 3.25", 4" (new anti-static wheels differ a few percent from nominal: measure, don't trust the label).
  • Motor cartridges: 100/200/600 RPM; external gear ratios change effective wheel RPM.
Measure your constants Track width, wheel diameter, and tracking-wheel offsets should be calibrated empirically, not read off CAD. A 2% wheel-diameter error is a 2% error in every distance the robot ever drives. Standard procedure: drive a known distance / spin N full rotations, compare reported vs actual, scale the constant. Build this calibration routine into your library as a first-class tool.

Odometry

LocalizationFoundation — everything depends on thisLemLib · EZ · WPILib

Dead-reckoning the robot's pose by integrating wheel and heading measurements. The bedrock of the entire library.

What it is

Odometry runs a fast loop (every 5–10 ms) that reads how far each tracking wheel turned since the last iteration, computes the small motion the robot made, and accumulates it into a global pose. It was popularized in VEX by the Pilons 5225A position-tracking paper and is what powers LemLib's chassis.getPose().

The math (arc-based update)

The per-iteration inputs are Δv from a parallel (vertical) wheel at horizontal offset ov from the tracking center, Δh from a perpendicular (horizontal) wheel at vertical offset oh, and heading change Δθ from the IMU. The robot is modeled as moving along a circular arc:

if Δθ = 0:   local_y = Δv,   local_x = Δh
else:   chord = 2·sin(Δθ/2)
         local_y = chord · (Δv/Δθ + ov)
         local_x = chord · (Δh/Δθ + oh)

Then rotate the local displacement into the global frame using the average heading of the iteration and accumulate:

θavg = θold + Δθ/2
x += local_y·cos(θavg) + local_x·sin(θavg)
y += local_y·sin(θavg) − local_x·cos(θavg)
θ += Δθ

(Signs depend on your coordinate convention. Derive them once, carefully, and unit-test them.)

Hardware configurations, best to worst

  1. IMU + 1 parallel + 1 perpendicular tracking wheel: the standard competitive setup. The perpendicular wheel captures sideways slide (getting bumped, drift during turns).
  2. IMU + 1 parallel tracking wheel: fine if the robot rarely translates sideways; can't see lateral pushes.
  3. IMU + drive IMEs: zero extra hardware; corrupted by wheel slip under acceleration and during pushing matches. Works surprisingly well with traction wheels and gentle accel limits (this is what many EZ-Template robots run).
  4. Two parallel wheels for heading (no IMU): the original Pilons method; heading from (ΔL − ΔR)/trackWidth. Strictly worse than an IMU on V5 today; only relevant as a fallback.
Pros
  • Fast, cheap to compute, smooth, always available
  • High relative accuracy over short distances
  • Enables every pose-based motion (move-to-point, pure pursuit, ...)
  • Well-documented; every top team runs it
Cons
  • Pure dead reckoning: error accumulates without bound
  • Blind to wheel slip, collisions, being pushed (partially mitigated by tracking wheels)
  • Sensitive to constants (wheel diameter, offsets) — needs calibration
  • Heading error is the killer: 1° of heading error becomes ~0.4" of position error per 24" driven

Implementation considerations

  • Run it in its own task/loop at fixed rate (10 ms is standard; 5 ms is fine on V5). Timing jitter degrades accuracy, so use "sleep until next period" (pros::Task::delay_until / vexide's sleep in a loop with an interval), not "sleep 10 ms after work."
  • Thread safety: pose is written by the odom task and read by motion tasks. In C++ guard it with a mutex or make it a single atomically-swapped struct; in Rust the borrow checker will force you to decide (e.g., Mutex<Pose> or a watch channel).
  • Prefer the IMU for Δθ over encoder-derived heading, but apply a calibrated scale factor (spin the robot 10× 360° and compare).
  • Expose setPose() so autons can declare the starting pose and so correction layers (MCL, GPS, wall resets) can overwrite it.
  • Keep velocity too: differentiate pose (low-pass filtered) or read wheel velocities — profiled motions and settling detection need it.
  • The euler-integration variant (skip the arc chord, assume straight-line motion each tick) is simpler and nearly as accurate at 10 ms loop times; the arc version costs little, so just do it right once.

IMU Fusion & Calibration

LocalizationLow effort, high payoff

The V5 inertial sensor is your heading source. Treat it well.

Why the IMU owns heading

Encoder-derived heading depends on track width being exact and both wheels never slipping — neither is true. The V5 IMU's gyro integration is far more robust for the 15 s – 2 min timescales of VEX matches. Its two real weaknesses are slow drift (usually well under 1°/min when healthy) and a constant scale error (reads e.g. 358.7° after a true 360° turn).

What to implement

  • Blocking calibration at startup with a clear on-screen indicator. Calibration takes ~2–3 s and the robot must be still; starting a match with a half-calibrated IMU ruins everything downstream. Handle the "calibration failed / timed out" case (retry once, then fall back to encoder heading and warn loudly).
  • Scale-factor correction: heading = raw_heading × k where k is measured by spinning ~10 rotations. Store per-robot in config.
  • Dual-IMU averaging (optional): two IMUs averaged (with per-unit scale factors) roughly halves random drift; some top teams do this. Cheap insurance if you have a spare port.
  • Accelerometer: mostly ignore it for localization (double-integration is hopeless), but it's useful for collision detection: a spike in |accel| can trigger MCL to widen its uncertainty or a motion to abort.
Mounting matters Mount the IMU rigidly near the center of rotation, on standoffs or a well-braced piece of structure; flex and vibration inject noise. Avoid mounting directly above motors (heat) or at the far end of a whippy cantilever.

Kalman Filtering

LocalizationSensor fusionWPILib-inspired

Statistically optimal blending of multiple noisy measurements. In VEX, most useful in small, targeted doses.

What it is

A Kalman filter maintains a state estimate and its uncertainty, alternating two steps: predict (advance the state with a motion model, uncertainty grows) and update (blend in a measurement, weighted by the ratio of model vs sensor uncertainty). The Extended (EKF) and Unscented (UKF) variants handle nonlinear models like drivetrain kinematics. WPILib's DifferentialDrivePoseEstimator is essentially odometry + a Kalman-style correction from vision measurements.

Where it earns its keep in VEX

  • 1-D velocity filtering: a tiny constant-gain Kalman filter (or just a well-chosen low-pass/SMA) on flywheel or drive velocity readings before feeding PID-F. Big quality-of-life win, trivial to implement.
  • Pose estimator pattern (recommended architecture): odometry as the predict step; sporadic absolute measurements (GPS sensor, distance-sensor wall fixes, MCL output) as updates, each weighted by trust. This gives you WPILib-style addVisionMeasurement() semantics: addAbsoluteMeasurement(pose, confidence).
  • Full EKF over (x, y, θ): doable, but honest covariance modeling of wheel slip is hard, and a mis-tuned EKF is worse than plain odometry. Most VEX teams get more from MCL + distance sensors than from a full EKF.
Pros
  • Principled fusion of any number of sensors with different noise levels
  • Smooth output; handles asynchronous measurements naturally
  • The "odometry predicts, absolute sensors correct" pattern is the right skeleton for your localization stack regardless
Cons
  • Needs noise covariances you can only guess at (tuning by vibes)
  • Unimodal: cannot represent "I'm near one of these two walls" — MCL can
  • Linearization (EKF) misbehaves under large heading error
  • Complexity rarely pays off vs. simpler weighted blending in VEX-scale problems

Implementation considerations

  • Start with the complementary-filter version: pose = (1−k)·odom_pose + k·absolute_pose applied only when an absolute measurement arrives, with k based on distance/quality. It's 90% of the benefit for 5% of the code.
  • Design your localization module around a PoseEstimator interface from day one — plain odometry is just the degenerate case with no update step. Then MCL/GPS slot in later without touching motion code.
  • If you do a real KF, keep the state small (x, y, θ or even just x, y with IMU heading passed through) and test against logged data on your computer, not on the robot.

Monte Carlo Localization (MCL / Particle Filter)

LocalizationAdvancedAbsolute correction

Represent the robot's belief as hundreds of hypothesis "particles," weighted by how well distance-sensor readings match the known field geometry.

What it is

MCL maintains N candidate poses (particles). Each loop:

  1. Predict: move every particle by the odometry delta, plus random noise (this models slip/uncertainty).
  2. Weight: for each particle, raycast from its pose to the field walls to compute what each distance sensor should read; weight the particle by how close the actual readings are (e.g., Gaussian likelihood).
  3. Resample: draw a new particle set proportional to weights (low-variance/systematic resampling), so belief concentrates around consistent hypotheses.
  4. Estimate: output the weighted mean (or best cluster) as the corrected pose.

Because the VEX field is a known 144"×144" box with known internal geometry, and the IMU gives you heading almost for free, VEX MCL usually only needs to estimate (x, y) with θ taken from the IMU — which dramatically shrinks the problem.

What it's used for

  • Killing accumulated odometry drift mid-auton (especially in long skills runs, 60 s of driving = a lot of drift).
  • Recovering after collisions or wheel-slip events that odometry can't see.
  • Skills routes that touch many field locations where a wall-alignment "ram reset" would waste time.
Pros
  • Provides absolute position — bounds error over a whole run
  • Multimodal: can hold several hypotheses until evidence disambiguates
  • Naturally fuses any number of distance sensors
  • Degrades gracefully: worst case it just follows odometry
  • Genuinely feasible on V5 (a few hundred particles at 50–100 Hz with efficient raycasts)
Cons
  • Most complex algorithm in this guide to implement and debug
  • Other robots and game objects create readings your wall model can't explain — must be filtered or MCL confidently teleports you
  • Needs a field model per game (walls + fixed goals/obstacles)
  • Tuning: particle count, motion noise, sensor noise model, resampling strategy
  • Distance sensors are weakest exactly when you need them (long range, shallow angles)

Implementation considerations

  • Sensor gating: reject readings that disagree wildly with the expected value at the current best estimate (they're probably a robot, not a wall). Also reject readings at extreme range or predicted shallow incidence angles.
  • Raycasting: against an axis-aligned box + a few rectangles is just a handful of ray-segment intersections; keep the field model as a small list of segments. Precompute per-sensor mounting transforms (offset + angle on the robot).
  • Noise injection is load-bearing: too little and particles collapse to a wrong answer they can't escape; too much and the estimate is jittery. Start with σ ≈ 0.5–1" per predict step and tune.
  • Recovery: keep a small fraction of particles randomly scattered (or trigger re-seeding when average likelihood collapses) so the filter can recover from kidnapping (big collision).
  • Output smoothing: don't hard-overwrite the odometry pose every loop — blend toward the MCL estimate, or run MCL as the correction source feeding the pose-estimator interface from the Kalman section.
  • 3–4 distance sensors pointing in different directions (e.g., front/left/right/back) makes the pose observable in most field locations; 1–2 sensors leaves large ambiguous regions.
  • Performance: use fixed-size arrays (no per-loop allocation), float not double if profiling demands it, and remember V5's CPU is a ~Cortex-A9: a few hundred particles × 4 raycasts is fine, don't fear it, but profile.
Cheap alternative: wall resets Before building MCL, implement one-shot distance-sensor resets: when you know you're facing a wall squarely, overwrite the corresponding pose coordinate from the sensor reading (x = 144 − reading − sensor_offset, etc.). EZ-style ram-into-wall resets (drive into wall, zero the coordinate) are the zero-sensor version. These two cover a large share of MCL's practical value at 2% of the effort, and the raycast/gating code you write for them is reusable inside MCL later.

VEX GPS Sensor

LocalizationAbsoluteSituational

Camera-based absolute pose from the coded strip on competition field walls.

The GPS sensor reads a printed pattern on the field perimeter and outputs an absolute field pose. As a sole localization source it's too noisy and too laggy for tight motion control, but as an absolute correction feeding your pose estimator it's nearly free accuracy.

Pros
  • True absolute pose with zero field-model code
  • Great for initial pose acquisition (no more hardcoding start poses per auton, in theory)
  • Complements odometry's failure modes exactly
Cons
  • Noisy (worse near field center) and moderate update latency
  • Occluded easily by robots/structures; needs clear sightline to the strip
  • Practice fields often lack the GPS strip (you can buy/print it)
  • Consumes a smart port and prime mounting real estate

Implementation considerations

  • Treat it exactly like a vision measurement in WPILib: poseEstimator.addAbsoluteMeasurement(gps_pose, quality), where quality derives from the sensor's reported error/signal and gets worse near field center.
  • Reject readings while rotating fast (motion blur) and obvious outliers more than a few inches from the current estimate (unless MCL/odometry confidence is already terrible).
  • Design so GPS is optional per-robot config — many of your users' robots (including possibly yours) won't mount one.

PID Control

Feedback controlFoundationEZ · LemLib · everywhere

The workhorse feedback controller. Every motion in your library is ultimately one or two PIDs (or a controller that replaces them).

What it is

PID computes an output from the error between target and measurement:

u = Kp·e  +  Ki·∫e dt  +  Kd·(de/dt)
  • P pushes proportionally to how far off you are. Does most of the work.
  • I accumulates persistent error to overcome friction/steady-state offset. In VEX drivetrains it's often left at 0 or used only near the target.
  • D resists rate of change, damping oscillation and overshoot.

Where PIDs live in a motion library

  • Lateral (distance) PID: error = remaining distance. Used by drive-straight and move-to-point.
  • Angular (heading) PID: error = wrapped heading difference. Used by turns, heading hold, and as the steering half of move-to-point/boomerang.
  • Mechanism PIDs: lift position, catapult angle, flywheel velocity (usually PID-F, see Feedforward).

The classic two-PID drive structure (this is EZ-Template's core, and LemLib's too):

loop every 10 ms:
    lat_out  = latPID.update(target_dist - traveled)
    ang_out  = angPID.update(wrap(target_heading - heading))
    left  = lat_out + ang_out
    right = lat_out - ang_out
    scale (left, right) so neither exceeds max_voltage   // preserve turn authority
    set motor voltages
Pros
  • Simple, well-understood, tunable by feel with a known recipe
  • Handles disturbances (defense, friction changes) automatically
  • Model-free: no robot characterization required
  • Composable: nearly every higher-level algorithm reuses it
Cons
  • Reactive only: without a profile or feedforward, aggressive gains overshoot and gentle gains crawl
  • One tune is only optimal for one robot mass/speed regime (retune when the robot changes)
  • Integral windup must be actively managed
  • Poor at tracking moving targets by itself (that's what feedforward is for)

Implementation considerations

  • One generic Pid class with: gains, output clamping, integral zone (only integrate when |e| is small), integral clamp (anti-windup), optional derivative low-pass filter, reset(). Every motion constructs its own instances from user-supplied gain sets.
  • Derivative on measurement (d/dt of the sensor, negated) instead of on error avoids the "derivative kick" when a target changes mid-motion — worth it since you'll retarget PIDs constantly for chained motions.
  • Voltage, not the built-in velocity controller: command motors in millivolts (move_voltage in PROS, voltage in vexide) so your PID is the only controller in the loop. Stacking your PID on VEX's internal velocity PID makes tuning nonsense.
  • Gain scheduling hooks: EZ-Template exposes different PID sets for short vs long drives and for turns vs swings. Make gain sets a parameter of the motion call with sensible defaults, not a global.
  • Tuning workflow you should ship: a test routine (buttons on the controller to run a canonical 24" drive / 90° turn repeatedly) plus live telemetry of error over time. Recipe: raise P until slight oscillation, raise D until it damps, add I only if steady-state error persists. This tooling is half of why EZ-Template is popular.

Feedforward

ControlWPILib-inspiredRequired for profiling & RAMSETE

Predict the voltage a motion needs instead of waiting for error to appear. The single biggest upgrade WPILib thinking brings to VEX code.

What it is

A simple motor/drivetrain model that maps desired velocity and acceleration directly to voltage:

u = Ks·sgn(v)  +  Kv·v  +  Ka·a
  • Ks (static): voltage to overcome friction and start moving.
  • Kv (velocity): voltage per unit of cruising speed. Roughly 12 V / free_speed.
  • Ka (acceleration): extra voltage per unit of acceleration.

Feedback (a small PID) then only corrects the residual error the model missed. This "feedforward does 90%, feedback cleans up" split is how WPILib executes trajectories, how good flywheels hold speed, and how your motion-profiled moves should drive.

Characterization (measuring the constants)

  1. Ks, Kv: slowly ramp voltage, log (voltage, steady velocity) pairs, fit a line: slope = Kv, intercept = Ks.
  2. Ka: apply voltage steps and fit acceleration response, or tune by hand until profiled moves track without lag.

Ship this as a built-in routine that prints constants to the terminal — it takes one carpet session and makes every profiled motion dramatically better.

Pros
  • Velocity tracking becomes nearly instant and overshoot-free
  • Makes motion profiles and RAMSETE actually work (they assume it)
  • Flywheel recovery time drops massively vs pure PID
  • Constants are physically meaningful and robot-portable in structure
Cons
  • Needs characterization; constants drift with battery voltage and wear
  • Model is linear; ignores battery sag, turning scrub, weight transfer
  • One more concept for users of your library to learn (make it optional)
Battery compensation V5 motor commands are effectively duty-cycle relative to battery voltage. For consistency across battery states, compute feedforward in volts and scale: command = u / battery_voltage × 12000 mV (capped). This one line noticeably improves auton repeatability between matches.

Exit Conditions & Settling

Control infrastructureEZ-Template's signature feature

Deciding when a motion is "done" is as important as the motion itself. Bad exit logic = autons that hang or move on too early.

The EZ-Template model (adopt this)

A motion exits when any of these fires:

ConditionLogicCatches
Settled (small error)|error| < small_tolerance continuously for small_timeout (e.g. 1" for 100 ms)Normal successful completion
Close enough (big error)|error| < big_tolerance continuously for big_timeout (e.g. 3" for 500 ms)Motion that's near but oscillating/crawling
Velocity stall|velocity| ≈ 0 for velocity_timeout while not settledRobot physically stopped (wall, game object) short of target
Current spike (mA)Motor current above threshold for mA_timeoutPushing against something immovable
Absolute timeoutElapsed > max_timeEverything else. Every motion must have one.

Implementation considerations

  • Make this a reusable ExitConditions / Settler object owned by each motion, configured with per-motion overrides and library-wide defaults. Both your PID motions and your path followers should use the same abstraction (for followers, "error" = distance to end of path).
  • Report why a motion exited (settled / stalled / timeout) as a return value. Invaluable for auton debugging, and lets user code react ("if we stalled, we hit the goal early — score now").
  • Velocity/current exits are what make wall-ram pose resets safe and fast: drive into the wall, exit on stall, reset the coordinate.
  • Tolerances are unit-sensitive: angular motions need degree-scale tolerances, lateral need inch-scale. Keep separate default sets.

Slew Rate Limiting

Control infrastructureEZ-style

Cap how fast commanded output can change, so the robot doesn't wheelie, slip, or throw its own odometry off the moment a motion starts.

A slew limiter clamps the change in output per loop: out += clamp(target_out − out, −rate·dt, +rate·dt). EZ-Template applies it at the start of drive motions (configurable distance/speed window); WPILib's SlewRateLimiter is the same idea applied to driver input or setpoints.

Pros
  • Prevents wheel slip → directly protects IME-based odometry accuracy
  • Prevents tipping with tall robots
  • Three lines of code
Cons
  • Crude compared to a real motion profile (no deceleration shaping)
  • Slows response if applied where it isn't needed (e.g., limiting decreases in output can prevent stopping quickly — usually only limit increases)
  • Interacts with PID tuning (tune with slew enabled)

Implementation considerations

  • Offer it in two places: (1) inside motions as an accel ramp on the output, (2) as a driver-control input shaper. Same class, two uses.
  • Once you have trapezoidal profiles, slew becomes the fallback for unprofiled motions. Keep both; profiles for planned moves, slew for everything reactive.

Drive Distance (EZ-style, odometry-tracked)

Point motionRelative → absolute bridge

"Drive 24 inches straight" with heading hold — but implemented so the global pose stays valid afterward.

What it is

A lateral PID on distance traveled plus an angular PID holding the heading captured at motion start (or a user-supplied heading). This is EZ-Template's bread-and-butter motion, and it's what makes autons easy to write when you think in tiles: forward 24, turn 90, forward 48.

The hybrid design (your library's differentiator)

Instead of measuring distance as "encoder ticks since motion start," compute an absolute target pose from the current odometry pose and drive to it:

fn drive_distance(d, params):
    start = odom.pose()
    target = (start.x + d·cos(start.θ),  start.y + d·sin(start.θ))
    // Option A: run distance-PID on projection of (pose − start) onto the start heading
    //           + heading PID locked to start.θ        (EZ feel, odometry-backed)
    // Option B: just call move_to_point(target)        (maximum reuse)

Option A preserves EZ's exact behavior (the robot fights to stay on the original line). Option B is less code but behaves differently when knocked off course (it steers to the point rather than back onto the line). Ship Option A as the default for "drive straight" semantics; either way the global pose remains correct for whatever motion comes next, which is the whole point.

Pros
  • Easiest mental model for writing autons quickly
  • Heading lock resists defense and drivetrain asymmetry
  • With odometry backing: freely mixable with move-to-point and paths
Cons
  • Purely reactive unless paired with slew or a 1-D profile
  • Relative targets compound placement error (each move starts from wherever the last one actually ended — absolute motions self-correct this, relative ones don't)

Turns & Swing Turns

Point motionEZ · LemLib

Point turns, swing turns, and turn-to-point. Deceptively simple; heading accuracy here compounds into everything else.

Variants to implement

  • Turn to heading: angular PID on wrapped error to an absolute heading. The fundamental one.
  • Turn to point: compute target_heading = atan2(p − pose) each loop (recompute live, don't precompute once) and run the same PID. Also the "aim at goal" primitive; support an offset angle and a "reverse" flag (point the back at it).
  • Swing turn (EZ signature): lock one side of the drive (hold at 0 or a bias voltage) and PID the other. Pivots around a wheel instead of the center. Great for hooking around game elements and for preserving position against a wall. Parameterize which side locks and optional locked-side speed (arc-ish swings).
  • Motion-profiled turn: trapezoidal profile on heading for big turns; faster and more repeatable than pure PID for >90° turns once tuned.

Implementation considerations

  • Always wrap error to (−180°, 180°]; support forcing a direction (cw/ccw) for cases where the short way is blocked.
  • Angular exit tolerances ~1–2° with a settle time; heading errors under 1° are usually not worth the settling time they cost.
  • Swing turns translate the robot as they rotate. With odometry this is fine (the pose tracks it), but the ending position depends on which side you swing; document this for users.
  • Expose max-voltage caps per motion; slow turns are dramatically more accurate for the last few degrees.

Move to Point

Point motionLemLib coreOdometry required

Drive to an (x, y) coordinate from wherever you are. The first big payoff of having odometry.

The algorithm (LemLib-style)

loop:
    dx, dy   = target − pose
    dist     = hypot(dx, dy)
    heading* = atan2(dy, dx)          (+180° if driving in reverse)
    e_ang    = wrap(heading* − pose.θ)

    lat_out  = latPID.update(dist)
    lat_out *= cos(e_ang)             // KEY: scale by heading alignment
    ang_out  = angPID.update(e_ang)

    if dist < settle_radius:          // don't spin when on top of the point
        ang_out = 0                   // hold last heading; just close distance

    left, right = lat_out ± ang_out   → scale to max, apply

Two details do all the heavy lifting:

  • The cos(e_ang) scaling automatically slows forward drive while badly misaligned (and drives backward if the point ends up behind), so you get a smooth arc instead of stop-turn-go.
  • The settle radius: as the robot reaches the point, atan2 becomes unstable (tiny position noise = huge heading swings). Inside ~3–7", freeze the angular target and let the lateral PID finish.
Pros
  • Position errors stop compounding: every call self-corrects to absolute field coordinates
  • Naturally produces efficient curved approaches
  • Small code on top of existing PIDs + odometry
  • With early exit, chains into fluid multi-point routes (poor man's pure pursuit)
Cons
  • No control over final heading (that's boomerang's job)
  • No control over the shape of the path taken (that's pure pursuit's job)
  • Quality is bounded by odometry quality
  • Arc behavior near obstacles can surprise users (the robot cuts curves)

Implementation considerations

  • Parameters per call: max speed, min speed (see chaining), forwards/backwards, early-exit range, timeout. LemLib's params-struct pattern with defaults is the right API shape.
  • A min-speed floor prevents the asymptotic crawl at the end of a P-controlled approach and is essential for chained motions.
  • Use the same ExitConditions object as everything else, with error = remaining distance.

Boomerang Controller (Move to Pose)

Point motionLemLib moveToPosePose target

Arrive at a point facing a specific direction, via a single curved motion. LemLib's moveToPose is a boomerang controller.

What it is

Boomerang turns a pose target into a moving point target. Each loop it computes a carrot point, pulled back from the target along the desired final heading, and runs move-to-point at the carrot:

h = distance(pose, target)
carrot = (xt − h·dlead·cos(θt),   yt − h·dlead·sin(θt))

where d_lead ∈ [0, 1] controls curve aggressiveness. Far away, the carrot sits well behind the target, so the robot approaches from the direction that lines it up; as h → 0 the carrot converges to the target and the robot arrives aligned with θt. At d_lead = 0 it degenerates to plain move-to-point.

Pros
  • Full pose control (position + final heading) with almost no code beyond move-to-point
  • No path planning or trajectory generation needed
  • Replaces "drive, stop, turn, drive" sequences with one fluid motion
Cons
  • Path shape is emergent, not specified: you can't guarantee clearance around obstacles
  • Final heading accuracy is soft (approach direction ≈ θt, not exact); tight heading tolerance needs a small finishing turn
  • d_lead is a feel parameter; too high makes wide loopy approaches, too low barely curves
  • Can behave oddly when the target is close but badly misaligned (consider a minimum-h clamp or fall back to turn-then-drive)

Implementation considerations

  • Reuse the move-to-point loop verbatim; boomerang is just a target-point supplier in front of it. This is a good test of your internal architecture.
  • Add a horizontal-drift term (LemLib exposes this): limiting speed by how hard the robot is turning (e.g., cap lat_out by a function of curvature) prevents tipping/sliding on sharp carrot chases.
  • Expose d_lead per call with a tuned default (~0.6 is a common starting point).
  • Same settle-radius trick as move-to-point, but settle on the target, not the carrot.

Motion Chaining & Early Exit

InfrastructureWhat separates fast autons from slow ones

Let one motion hand off to the next without stopping. This is a library feature, not an algorithm, and it needs to be designed in from the start.

The idea

Full settling (decelerate, hold, verify) costs 200–500 ms per motion. In a 10-motion auton that's 2–5 seconds. If the next motion is roughly "in the same direction," you can exit the current one early, at speed, and let the next controller take over:

  • Early-exit range: "consider this move done when within R inches of the target" (LemLib's earlyExitRange). The next motion inherits the momentum.
  • Min speed: don't let the controller decelerate below vmin during a chained segment, so momentum carries through the handoff.
  • Async motions + cancellation: start a motion without blocking, do other things (spin intake, wait for a sensor), then cancel/override it. Requires every motion to be cancel-safe.

Implementation considerations

  • Because all motions share the global pose, a chained handoff is trivial: the next motion just reads the current pose like always. This falls out of the hybrid design for free.
  • Only one motion may command the drivetrain at a time. Enforce it structurally: a single "motion executor" task/future that owns the motors, with new requests replacing the current one (see Concurrency).
  • Blocking API = call runs to completion; async API = returns a handle you can await/waitUntilDone()/cancel. Provide both; beginners use blocking, advanced autons use async. LemLib does this with waitUntil/waitUntilDone; in vexide, futures give it to you natively.
  • Chained exits skip settling, which means position error at handoff. Follow a chain with one settling motion (or an absolute-target motion, which self-corrects) before anything precision-critical like scoring.

Path Generation (Splines)

Path planningInput to pure pursuit & profiling

Turning a handful of waypoints into a smooth, dense sequence of points a follower can track.

Spline options

TypeDefined byCharacterNotes
Cubic Bézier4 control points per segmentIntuitive to drag in a GUI; heading at endpoints controlled by control-point directionWhat LemLib paths and path.jerryio use; the pragmatic default
Cubic/Quintic HermitePoint + tangent (+ curvature for quintic) per waypointWaypoint-centric; quintic gives continuous curvature (no lateral-accel jumps)WPILib trajectories use these; quintic is nicer for RAMSETE
Catmull-RomJust the waypointsPasses through every waypoint automaticallyEasiest UX, least control over shape near points

From spline to followable path

  1. Sample the spline densely (e.g., every 0.25–0.5"). Arc-length parameterize (equal spacing along the curve, not equal t).
  2. Compute curvature κ at each sample (from first/second derivatives, or the circumradius of neighboring points).
  3. Assign target velocities: cap by max speed and by curvature (v ≤ sqrt(a_lat_max / κ) or the simpler v = min(v_max, k / κ) heuristic), then run a backward pass so the robot can actually decelerate in time (v[i] = min(v[i], sqrt(v[i+1]² + 2·a_max·Δd))), and a forward pass for acceleration limits.

The result (point, heading, curvature, velocity) per sample is a path for pure pursuit, or with timestamps a trajectory for RAMSETE.

Implementation considerations

  • Precompute everything. Generate paths at compile time, at program start, or offline in a GUI; never sample splines inside the control loop. V5 has the CPU for startup generation of a whole auton's paths.
  • Support loading paths from a file format compatible with path.jerryio so you get a free visual editor. A custom web-based editor is a great later project but not a prerequisite.
  • Keep the path type follower-agnostic: pure pursuit, RAMSETE, and telemetry replay should all consume the same struct.

Motion Profiling

Path planningFeedforward-drivenWPILib · OkapiLib

Plan velocity over time before moving, then execute the plan with feedforward. The alternative philosophy to reactive PID.

1-D profiles (drives and turns)

A trapezoidal profile for a move of distance d: accelerate at amax to vmax, cruise, decelerate to 0 (a triangle if d is too short to reach vmax). Each loop, look up the profile's target velocity/position for the current time and command:

u = FF(vtarget, atarget) + PID(xtarget − xactual)

S-curve (jerk-limited) profiles additionally ramp acceleration, trading a little time for much less wheel slip and chassis rock. Asymmetric profiles (accelerate hard, decelerate gently) are often the practical sweet spot.

2-D profiles (trajectories)

The path-generation pipeline above, with timestamps: at each time t the trajectory specifies pose, velocity, and angular velocity. Executed open-loop it already looks impressive; closed with RAMSETE it becomes robust. This is exactly WPILib's trajectory stack.

Pros
  • Extremely repeatable: same move takes the same time, every run
  • Respects physical limits by construction (no slip, no tip)
  • Known duration = easy auton choreography ("intake spins up 0.4 s before arrival")
  • Smooth motion preserves odometry accuracy
Cons
  • Requires decent feedforward constants (characterization)
  • Time-based: a collision leaves the target marching ahead without you (mitigations: RAMSETE, abort-on-large-error)
  • Doesn't self-correct starting-position error unless closed with a pose-aware follower
  • More moving parts than PID-to-target

Implementation considerations

  • Start with 1-D profiles for drive-straight and big turns; they slot into the EZ-style API invisibly (same function signature, better motion).
  • Parameterize by distance rather than time where possible ("what should my velocity be at this remaining distance") — distance-parameterized execution degrades more gracefully under disturbance than time-parameterized.
  • Constraints (vmax, amax) should be per-call overridable; you'll want gentler profiles when carrying game objects high.

Pure Pursuit

Path followerLemLib · classic VEXGeometric

Chase a lookahead point that slides along the path ahead of the robot. The most popular path follower in VEX for good reason.

The algorithm

  1. Find the lookahead point: intersect a circle of radius L (centered on the robot) with the path, taking the intersection furthest along the path (never backward; track a monotonically advancing path index so you don't re-acquire earlier loops of self-crossing paths).
  2. Steer toward it. In local coordinates the required arc curvature is:
    κ = 2·xlocal / L²
    where xlocal is the lookahead point's lateral offset in the robot frame.
  3. Convert (v, κ) to wheel speeds: v_left = v·(1 − κ·track/2), v_right = v·(1 + κ·track/2), with v from the path's velocity plan (or a simple curvature-based slowdown).

Lookahead distance L, the one tuning knob

  • Small L: tight tracking, but oscillates/overshoots at speed.
  • Large L: smooth and stable, but cuts corners hard.
  • Adaptive L (scale with current speed, or store per-waypoint lookahead in the path) gets you both; worth implementing once the fixed version works.
Pros
  • Position-parameterized, not time-parameterized: get bumped, and it just keeps following from wherever it is. Very robust to disturbance
  • Simple geometry, easy to visualize and debug (draw the circle and point on the brain screen)
  • Explicit path shape = obstacle clearance you can actually plan
  • No characterization strictly required to get running
Cons
  • Systematically cuts corners (inherent to lookahead geometry)
  • End-of-path behavior needs special handling (lookahead runs off the path; finish with move-to-point at the final pose)
  • No inherent velocity plan; pair with path velocities for speed control
  • Tracking accuracy mid-path is "good," not "exact" — fine for VEX, but it's not a trajectory tracker

Implementation considerations

  • Robustness details that separate working implementations from flaky ones: handle "no intersection" (fall back to closest path point), never search backward, and switch to move-to-point for the last ~L of path.
  • Support reversed driving (following the path backward with the rear of the robot leading); it's mostly sign discipline.
  • Use path curvature to pre-slow into sharp turns (the backward-pass velocities from path generation), otherwise the robot enters corners hot and blows the line wide.
  • Exit conditions: distance-to-end below tolerance, plus the standard stall/timeout set.

RAMSETE Controller

Trajectory followerWPILib flagshipTime-parameterized

A nonlinear feedback controller that tracks a full trajectory (pose + velocity vs time) with proven convergence. WPILib's standard auton follower, rare but powerful in VEX.

What it is

Given the trajectory's desired state (pose, vd, ωd) at the current time and the pose error (ex, ey, eθ) expressed in the robot frame, RAMSETE outputs corrected velocities:

k = 2ζ·√(ωd² + b·vd²)
v = vd·cos(eθ) + k·ex
ω = ωd + k·eθ + b·vd·sinc(eθ)·ey

Those (v, ω) go through inverse kinematics to wheel velocities, executed with feedforward + velocity PID. Two gains: b (aggressiveness, >0) and ζ (damping, 0–1), famously insensitive; WPILib's defaults (b=2.0, ζ=0.7 in meters) barely ever need touching.

Pros
  • Tracks the path and the velocity plan: exact timing, minimal corner cutting
  • Mathematically guaranteed convergence; gains barely need tuning
  • The right closer for 2-D motion profiles (open-loop profile + RAMSETE = the WPILib recipe)
Cons
  • Needs the full stack below it: trajectories with timestamps, feedforward, wheel-velocity control, good odometry. It's the top of a pyramid
  • Time-parameterized: physical blockage → target marches on → aggressive catch-up when freed (add error-magnitude aborts)
  • Overkill for motions shorter than a couple of feet
  • Little VEX prior art to crib from vs pure pursuit

Implementation considerations

  • Unit sensitivity: the b and ζ defaults are calibrated for meters. If your library is inch-native, convert to meters inside the controller (or re-derive gains) or it will misbehave.
  • Implement sinc(x) = sin(x)/x with the x→0 limit (=1) handled explicitly.
  • Build order that works: feedforward → 1-D profiles → 2-D trajectories executed open-loop → add RAMSETE. Each stage is independently useful.
  • Consider offering both followers over the same path type and letting users pick: pure pursuit for robustness, RAMSETE for precision timing.

Stanley, LTV & Other Followers

Path followersAware-of, not must-build

The rest of the follower zoo, briefly, so you know what exists and why you'd (mostly) skip it.

Stanley controller

Steers from cross-track error at the front axle plus heading error: δ = e_θ + atan(k·e_lat / v). Famous from the DARPA Grand Challenge; designed for car-like (Ackermann) steering. On differential drives it offers little over pure pursuit; tracks tighter in some regimes but is twitchier at low speed. Skip unless curious.

LTV unicycle controller

A linear-time-varying state-feedback controller (gains from a lookup/Riccati solution scheduled on velocity). WPILib now recommends it over RAMSETE as its default trajectory follower: same role, better-behaved error response. If you build the RAMSETE stack, adding LTV later is a drop-in swap of the control law. Reasonable "v2" feature; the precomputed-gain-table approach avoids solving Riccati equations on the brain.

Model Predictive Control (MPC), LQR path tracking

Optimization-based tracking; genuinely better disturbance handling, genuinely not worth the complexity on a V5 brain for VEX-scale problems. LQR is practical for single mechanisms (see Mechanisms). File under "cool senior-year experiment."

2-D motion-profiled point moves (no path)

A middle ground worth knowing: apply a trapezoidal velocity plan to the move-to-point/boomerang distance term. You get profile smoothness without any path infrastructure. Several modern VEX templates do this quietly, and it's a natural extension once you have profiles.

Flywheels, Lifts & TBH

Beyond the drivetrainReuse your control toolbox

The same controllers, pointed at mechanisms. A good library exposes its PID/FF/profile primitives for arbitrary subsystems, not just the chassis.

Velocity control (flywheels)

  • PID-F (recommended): feedforward (Kv·vtarget + Ks) does almost all the work; a small P on velocity error trims. Filter the velocity measurement (V5 raw velocity is noisy).
  • Take-Back-Half (TBH): a VEX-classic integrator scheme: integrate error; on each error sign flip, set output to the average of current output and the output at the last crossing. One gain, decent recovery, no model needed. Historically popular; PID-F with real feedforward generally beats it now, but it's cheap to include for completeness.
  • Bang-bang: full power below target, zero (or coast) above. Fastest possible recovery, at the cost of ripple; a bang-bang-then-PIDF hybrid (bang-bang far from setpoint, PIDF near) is a strong practical choice.

Position control (lifts, arms, wall-stake mechs)

  • PID with gravity feedforward: for a rotating arm add Kg·cos(arm_angle); for an elevator a constant Kg. Removes droop and lets you soften P.
  • Trapezoidal-profiled position moves ("motion magic" style) reuse your 1-D profile code verbatim.
  • LQR on a characterized (Kv, Ka) model is the WPILib-style upgrade; optional, educational, genuinely smooth.

Library takeaway

Structure controllers (Pid, Feedforward, Profile, Tbh, Settler) as standalone, motor-agnostic components in a control module, with the chassis merely their biggest customer. Users will build better robots with your primitives than you can anticipate.

Holonomic Drives (X-drive / Mecanum)

Beyond tankDesign for it, even if you ship tank-first

Drives that translate in any direction independent of heading. Rare in modern high-level VEX (tank dominates for pushing power), but supporting them cleanly is an architecture question you should answer early.

  • Kinematics abstraction (the WPILib lesson): make motion controllers output a ChassisSpeeds {vx, vy, ω}, and let a drive-specific kinematics layer map it to wheel outputs. Tank kinematics simply rejects/ignores vy; X-drive and mecanum use their inverse-kinematics matrices. Controllers never know what drivetrain exists.
  • Holonomic point moves are easier: move-to-point becomes two independent axis PIDs (or one vector PID) plus a completely separate heading PID; you can translate and rotate simultaneously (WPILib's HolonomicDriveController pattern).
  • Odometry changes: wheel-based odometry needs the holonomic forward kinematics (or better, two tracking wheels + IMU, which works unchanged).
  • Field-centric driver control falls out for free: rotate the joystick vector by −θ before kinematics.
Practical scope call Ship tank-drive support first (it's what you and 95% of teams run), but route everything through ChassisSpeeds + a Kinematics trait/interface from day one. Retrofitting this abstraction later touches every motion; having it early costs almost nothing.

Library Architecture

DesignThe part most templates get wrong

How to structure the code so both the C++ and Rust versions are the same library in two languages.

Layered design

┌──────────────────────────────────────────────────────────┐
│  User API      chassis.moveToPoint(...), driveDistance() │
├──────────────────────────────────────────────────────────┤
│  Motions       MoveToPoint, Boomerang, PurePursuit, ...  │  ← one motion active at a time
├──────────────────────────────────────────────────────────┤
│  Control       Pid, Feedforward, Profile, Settler, Slew  │  ← pure math, reusable anywhere
├──────────────────────────────────────────────────────────┤
│  Localization  Odometry → PoseEstimator ← MCL, GPS, walls│  ← background task, owns the pose
├──────────────────────────────────────────────────────────┤
│  Kinematics    ChassisSpeeds ↔ wheel speeds              │
├──────────────────────────────────────────────────────────┤
│  Hardware      Motors, IMU, Rotation, Distance  (PROS /  │  ← the ONLY platform-specific layer
│                vexide wrappers behind thin interfaces)   │
└──────────────────────────────────────────────────────────┘

Principles that pay off

  • Keep the math pure. Control and localization algorithms should be plain functions/structs with no I/O, no sleeping, no motor handles: inputs in, outputs out. This is what makes them unit-testable on your laptop and portable between the C++ and Rust versions nearly line-for-line.
  • One pose, one owner. The localization task is the only writer of the pose; everything else reads through one accessor. All corrections (MCL, GPS, setPose) funnel through the same interface.
  • Motions are data + a step function. Model each motion as a state machine with init(pose), step(pose, dt) → ChassisSpeeds | Done(reason). A single executor loop runs whichever motion is active. This gives you chaining, cancellation, telemetry, and simulation hooks in one place, instead of each motion owning its own while-loop and motor writes (the classic template mistake).
  • Configuration as data. Robot constants (track width, wheel diameter, gains, sensor ports/offsets) live in one config struct the user fills out, like EZ-Template's constructor. No magic numbers inside algorithms.
  • Shared design document. Write the API spec (names, parameters, semantics, units) once, language-neutrally; implement it twice. Otherwise the two versions will drift into different libraries.

Concurrency: PROS Tasks vs vexide Async

PlatformBiggest structural difference between your two versions

Same architecture, two execution models. This is where the ports genuinely differ.

PROS (C++): FreeRTOS preemptive tasks

  • Spawn a dedicated odometry task (pros::Task) at 10 ms; optionally a separate motion-executor task.
  • Shared state (the pose, the active motion) must be guarded: pros::Mutex, or copy small structs atomically. Data races here are the classic source of once-a-week heisenbugs.
  • Blocking motion calls are natural: the user's auton function sleeps while the executor works; async = return immediately + waitUntilDone() polls a flag.
  • Watch task priorities and never starve the kernel: every loop must delay. Use delay_until for fixed-rate loops.

vexide (Rust): cooperative async/await

  • No RTOS: vexide runs its own async executor on bare metal. Your odometry loop is an async task (spawn) that sleep(10ms).awaits each iteration.
  • Motions are natural Futures: chassis.move_to_point(x, y).await is the blocking API, and not awaiting (or using select!/spawn) is the async API. Cancellation = dropping the future, which Rust makes well-defined; design motions to stop motors on drop (RAII guard).
  • Sharing the pose: Rc<RefCell<…>> or embedded sync primitives; the compiler forces you to get ownership right up front, which is annoying on day one and priceless on day thirty.
  • Cooperative scheduling caveat: a long computation (MCL resample over many particles) blocks every other task until it yields. Chunk heavy work or yield periodically; there's no preemption to save you.
Design implication The "motion = state machine stepped by an executor" model from the architecture section maps cleanly onto both: in PROS the executor is a task, in vexide it's an async loop. If you instead write motions as functions with internal while-loops, the two codebases diverge structurally and you'll maintain two different libraries. This one decision keeps the ports aligned.

API Design

DesignErgonomics = adoption

What the user-facing surface should look like, stealing the best ideas from LemLib and EZ-Template.

Patterns worth copying

  • Params-struct with defaults (LemLib): chassis.moveToPoint(24, 48, 2000, {.maxSpeed=90, .forwards=false}). In C++ use designated initializers on a params struct; in Rust use a builder or ..Default::default() struct update. Avoid 9-positional-argument functions.
  • Global defaults + per-call overrides (EZ): set default gains/exits once in the chassis constructor; override per call only when needed.
  • Blocking by default, async available: beginners write linear autons; experts overlap motions with mechanism actions.
  • Every motion takes a timeout. Non-negotiable; a hung auton is worse than a wrong one.
  • Return exit reason (settled / early-exit / stall / timeout) rather than void.

Units and type safety

  • Rust: newtypes or the uom crate give compile-time unit checking cheaply. At minimum, distinct Angle and Length types with explicit constructors (Angle::from_degrees(90.0)) kill the radians/degrees bug class outright. vexide's ecosystem already leans this way.
  • C++: user-defined literals (24_in, 90_deg) and thin wrapper types get you most of the same protection (OkapiLib did exactly this). It's more boilerplate than Rust but well-trodden.
  • If you skip typed units in C++, at least standardize (inches, degrees-at-API/radians-internal) and document relentlessly.

Naming & docs

  • Mirror names across both versions (moveToPoint / move_to_point) so docs and tutorials serve both.
  • Write docs as you go: LemLib's adoption owes as much to its documentation site as its code. Doxygen (C++) and rustdoc give you API references nearly free; add a tutorial path (install → configure → first auton → tuning) on top.

Tuning & Telemetry

ToolingWhy people actually adopt templates

Users don't adopt libraries for their algorithms; they adopt them for how fast they can get tuned and see what's happening.

  • Built-in tuning mode (EZ's killer feature): a controller-driven menu to run canonical test motions (24" drive, 90° turn, swing) repeatedly, tweak the active gain set live with the joysticks/buttons, and print results. Ship this in v1.
  • Brain-screen dashboard: live pose readout, a mini field view drawing the robot and active path/target (both PROS and vexide can draw to the screen; PROS ships LVGL), odometry health (are tracking wheels moving?), IMU status, per-motion exit reason of the last motion.
  • Data logging: log timestamped pose/target/output rows to the SD card or stream over serial; plot on a computer. A python plot script in the repo (error vs time, actual-vs-target path overlay) is worth more than any amount of on-screen squinting.
  • Auton selector: every team needs one (screen buttons or a port-mounted potentiometer); it's cheap for you to provide and heavily used. EZ ships one; users expect it.
  • Calibration routines as library functions: wheel-diameter scale, IMU scale, track width, feedforward characterization. Each prints the constant to paste into config.

Testing & Simulation

ToolingWhere pure-math architecture pays off

You can't unit-test a robot, but you can unit-test almost everything your library does before it touches one.

  • Host-side unit tests for all pure math: angle wrapping (the #1 regression source), odometry updates against hand-computed cases, PID behavior, profile generation, path sampling, pure-pursuit intersection edge cases, boomerang carrot math, RAMSETE outputs vs known-good WPILib values. Rust: cargo test works out of the box if your core crate is platform-independent (keep algorithms in a separate no_std-friendly crate from the vexide glue). C++: same idea with a separate CMake target + Catch2/GTest that never includes PROS headers.
  • Kinematic simulation: a ~50-line differential-drive model (integrate commanded wheel speeds with a velocity lag constant) lets you run entire autons headlessly and plot the path. Catches sign errors, tuning disasters, and logic bugs in seconds instead of field-time.
  • Replay testing: log real sensor data on the robot, re-run localization offline against it. This is the only sane way to develop MCL: record a drive with ground-truth checkpoints, iterate the filter at your desk.
  • CI: both repos should build + run host tests on every push (GitHub Actions has PROS and Rust toolchains covered). Publish releases as a PROS template (pros make template style) and a crates.io crate respectively.

  • Build system and header hygiene are a tax on library authors specifically
  • No standard package/test story; you assemble your own

Rust / vexide for this library

Pros
  • The shared-pose / task-safety problems that plague C++ templates are compile errors, not field failures
  • Async futures are a genuinely better model for motions: await, select! (first-of: motion done OR ring detected), timeout wrappers, and cancellation-by-drop all come from the language
  • Enums + pattern matching model motion state machines and exit reasons beautifully
  • cargo gives tests, docs, publishing, and dependencies for free — library-authoring ergonomics C++ can't match
  • Fresh ecosystem: your library could become the Rust VEX motion library (evian is the only major prior art)
Cons
  • Cooperative scheduler: heavy computation must be manually chunked/yielded or it stalls control loops
  • Pre-1.0 platform churn: vexide API changes will occasionally break you
  • Small community = fewer examples, fewer users, fewer contributors, less Stack-Overflow-ability
  • Borrow checker friction is highest exactly in shared-mutable-state robotics patterns (expect Rc<RefCell> and rearchitecting sessions early on)
  • Unofficial platform: VEX support channels won't help; competition legality has been fine but is your responsibility to verify each season

Recommendation

  • Write the language-neutral design spec first (API names, units, motion semantics, config schema). This document is the real library; the two codebases are renderings of it.
  • Prototype algorithms in whichever language you'll compete with this season, so field time validates the math. For most people that's C++/PROS purely because of ecosystem gravity and teammate familiarity.
  • Port to the second language once each subsystem stabilizes, not in lockstep. Porting after the design settles is fast (the math layer moves almost mechanically); porting during churn doubles every redesign.
  • If the goals are learning and building something distinctive (rather than maximum adoption), inverting this and going Rust-first is a defensible choice; the compile-time safety will also catch design flaws the C++ version would have let slide.

Suggested Roadmap

A build order where every stage produces something competition-usable.

  1. Skeleton & hardware layer: config struct, motor/sensor wrappers, telemetry logging, fixed-rate loop utility. Deliverable: pose printed to screen.
  2. Odometry + IMU: tracking task, calibration routines, setPose, brain-screen field view. Deliverable: push the robot around, watch the pose stay honest.
  3. PID motions + exit conditions + slew: drive distance (odometry-backed), turn to heading, swing turns, the Settler, tuning mode. Deliverable: an EZ-Template equivalent. Usable in competition now.
  4. Move to point, turn to point, boomerang: the LemLib layer. Deliverable: point-based autons.
  5. Motion chaining: async motions, early exit, min speed, cancellation. Deliverable: fluid multi-step autons.
  6. Feedforward + 1-D profiles: characterization routine, profiled drives/turns. Deliverable: repeatable fast motions.
  7. Path generation + pure pursuit: Bézier sampling, velocity passes, follower, path.jerryio import. Deliverable: skills-run routes.
  8. 2-D trajectories + RAMSETE (or LTV): timed profiles closed with the nonlinear follower. Deliverable: WPILib-grade trajectory tracking.
  9. Absolute localization: distance-sensor wall resets → pose-estimator interface → GPS input → MCL. Deliverable: drift-free 60 s skills runs.
  10. Polish: docs site, examples, auton selector, simulation scripts, second-language port catch-up, release packaging (PROS template / crates.io).
Scope honesty Stages 1–5 are a season's worth of solid work for one person alongside actually competing. Stages 6–9 are what make the library special. Resist starting MCL before stage 3 is bulletproof; every advanced feature stands on odometry + exits being trustworthy.

Resources

The references this guide distills, and where to go deeper.

VEX libraries to study

  • LemLib + its docs — odometry, moveToPoint/Pose (boomerang), pure pursuit, the params-struct API.
  • EZ-Template + docs — PID motions, swing turns, exit conditions, tuning workflow, auton selector.
  • OkapiLib — typed units in C++, motion profiling, chassis abstraction (bundled with PROS).
  • evian — the reference for how motion control is structured in Rust on vexide.

Platforms

  • PROS 4 documentation — kernel API, tasks, motors, sensors.
  • vexide + GitHub — Rust runtime, async model, cargo-v5.
  • Purdue SIGBots (BLRS) wiki — the best general VEX software/hardware knowledge base, including odometry and control write-ups.

Theory & algorithms

  • Pilons 5225A "Introduction to Position Tracking" — the VEX odometry paper everyone implements.
  • WPILib docs — feedforward & characterization, kinematics, trajectory generation, RAMSETE/LTV, pose estimation. The single richest source to mine for your library's advanced features.
  • Controls Engineering in FRC (Tyler Veness) — free book covering PID through state-space/LQR with robotics framing; the math behind everything in this guide.
  • R. Craig Coulter, "Implementation of the Pure Pursuit Path Tracking Algorithm" (CMU tech report) — the original pure-pursuit reference.
  • Thrun, Burgard, Fox, Probabilistic Robotics — the MCL/particle-filter bible (chapter 8).
  • Desmos/community boomerang demos and the VEX forum "boomerang controller" threads — the practical tuning lore for d_lead.

Tools

  • path.jerryio — visual path editor with LemLib-compatible export.
  • Any serial plotter / a small matplotlib script — for tuning telemetry. Build the logging first; the plots pay for themselves the first session.
